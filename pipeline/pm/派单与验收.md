# PM 派单与验收（流水线专用）

> 与通用 PM 模板的区别：这里的验收**不靠人回忆判据**，靠 `08_gates.json`。
> PM 只做三件人才能做的事：定 WARN 是否可接受、判"算得对不对"、决定打回还是放过。

---

## 一、RACI（角色绑到具体专家）

| 阶段 | 负责（R） | 绑定专家 ID | 审批（A） | 协作（C） |
|---|---|---|---|---|
| S0 规格 | 因子建模师 | `quant-factor-modeler` | PM | 数模分析 |
| S1 数据与股票池 | 数据工程 | `a-share-data-expert` | PM | 因子建模师 |
| S2 单季化 | 因子建模师 | `quant-factor-modeler` | PM | 数据工程 |
| S3 时点 | 数据工程 + 合规 | `a-share-data-expert` / `capital-market-compliance-officer` | PM | — |
| S4 计算 | 因子建模师 | `quant-factor-modeler` | PM | 数模分析 |
| S5 标准化 | 量纲处理 | `data-normalization-analyst` | PM | 因子建模师 |
| S6 评价 | 数模分析 | `quant-indicator-analyst` | PM | `market-regime-analyst` |
| S7 报告 | 数模分析（写）+ PM（核） | `quant-indicator-analyst` / `project-delivery-manager` | PM | 合规检验官 |

**A 列只有 PM**。任何阶段不得自审自批——执行者不能同时是验收者。

机器可读版在 `config/owners.json`，`python src/run.py --owners` 可直接打印；每条门禁结果里也带 `owner` / `expert` / `human_review`。

### 什么由代码做，什么由专家做

| 类型 | 承担者 | 内容 | 边界 |
|---|---|---|---|
| 算 | 代码 | 单季化、对齐、回归、标准化、IC、分层、净值、换手 | 不需要 agent |
| 卡 | 代码 | 26 条门禁 | **禁止 agent 改判** |
| 定口径 | 专家 | 公式、去累计、回归设定、中性化方案 | 只能给口径，不能改门禁 |
| 解释 | 专家 | 经济逻辑、是否只是行情 beta | 不参与验收 |
| 放行 | PM | 判 WARN、判"算得对不对"、出结论 | 只能 PM |

**不外包给 agent 的三件事**：门禁判定、spec 变更（必须走变更单）、验收结论。

## 三、验收单模板

```
验收单号：A-<任务单号>
执行方：<agent/人>
验收方：PM
门禁结果：PASS __ / WARN __ / FAIL __
WARN 处置：<逐条：接受/要求整改 + 理由>

人工复核（门禁管不到的部分）：
  □ 公式是否等于研报定义（对照截图/原文，逐符号）
  □ 股票池是否符合经济含义（金融股是否该剔除）
  □ 中性化前后结论是否一致（不一致要解释）
  □ 分层单调是"真单调"还是"两端翘"（看数值不看形容词）
  □ 扣费假设是否符合实际交易（佣金/印花/冲击）
  □ 结论是否超出数据边界（是否暗示预测/荐股）

结论：通过 / 有条件通过 / 打回 / 无法验收 / 拒收
整改项：<编号 + 内容 + 完成标准 + 复核时点>
```

**五级结论，不允许"基本可以"。**

| 结论 | 含义 | 下一步 |
|---|---|---|
| 通过 | 门禁全绿 + 人工复核无疑点 | 进入下一环节 |
| 有条件通过 | 门禁全绿，但有人工复核项需补说明 | 补说明后转通过；不得直接对外 |
| 打回 | 任一门禁 FAIL，或公式与原研报不符 | 只写缺什么，不替对方设计解法 |
| 无法验收 | 缺关键产物/数据不可得，无法判断 | 补数据或缩范围重派 |
| 拒收 | 存在前视、编造数值、篡改判据 | 记录并重做，不接受修补 |

## 四、门禁与人判的分界

| 门禁能管（有没有） | 门禁管不了（对不对） |
|---|---|
| 指标是否齐全 | 指标算得对不对 |
| 是否用了公告日 | 公告日数据本身准不准 |
| σ 是否无偏 | 回归设定是否符合经济逻辑 |
| 是否中性化 | 中性化后经济含义是否还在 |
| 成本是否扣了 | 成本假设是否贴近真实 |
| 报告是否有五节 | 结论是否越界 |

**所以 PM 的活没有被门禁取代，只是从"记 25 条判据"变成"判 6 件事"。**

## 五、变更留痕

任何 spec 改动都必须记录，否则两版结果不可比：

```
变更单：C-<序号>
改了什么：<字段：旧值 → 新值>
为什么改：<看到结果之后改的？如果是，必须写明并视为新实验>
影响范围：<重跑哪些阶段>
新结论是否覆盖旧结论：是/否（否 → 两版并列保留）
```

**看到结果再改参数 = 新实验，不是修 bug。** 这一条必须写进变更单，否则就是过拟合洗白。

---

## 六、PM 自己也要被约束

1. 不得把 FAIL 改判为 WARN —— 要改就改门禁代码，并走变更单。
2. 不得替执行方调参让门禁通过。
3. 不得在报告未生成时口头说"结果不错"。
4. 不得省略"与上期结论对照"——上期错了也要写。
5. 不得同时担任执行者与验收者；若人手不足，至少换一个 agent 执行。
