# 研报复现流水线 · 骨架

> 一句话：把「读研报 → 写代码 → 看 IC 图 → 说有效」这条靠人盯的链路，切成 8 个阶段，每阶段有固定产物和代码化门禁。
> PM 不再靠记性验收，跑一遍 `python src/run.py` 就知道卡在哪。

---

## 一、流程骨架

```
              ┌──────────────────────────────────────────────────────────┐
              │  规格（config/factor_spec.json）—— 唯一真源，先写后跑     │
              └───────────────────────────┬──────────────────────────────┘
                                          ↓
 S0 规格校验 ──► S1 数据接入 ──► S2 单季化 ──► S3 时点对齐
   G0(2)         G1(3)           G2(2)          G3(2) ★前视红线
                                                    ↓
 S7 报告 ◄── S6 评价 ◄── S5 截面标准化 ◄── S4 因子计算
   G7(4)      G6(4)         G5(4)            G4(5)
     ↑
     └── 任何一阶段 FAIL → 停止，不出报告，不进入下一步
```

星号（★）是**不可让步**的三处：时点（G3）、σ 无偏（G4.2）、成本（G7.1）。

## 二、八阶段：谁做、产出什么、怎么算过

| 阶段 | 干什么 | 产物 | 责任方 | 门禁 | 打回条件 |
|---|---|---|---|---|---|
| **S0 规格校验** | 把因子口径写成结构化 spec，检查必填项 | `00_spec.json` | 因子建模师（`quant-factor-modeler`） | G0.1–G0.2 | 缺公式/缺成本/缺调仓规则 |
| **S1 数据接入** | 载入价格与财报长表，**按 spec 过滤股票池**，统计覆盖 | `01_coverage.json` | 数据工程（`a-share-data-expert`） | G1.1–G1.3 | 股票数 <50、公告日 <8、缺失率未披露、股票池未按 spec 执行 |
| **S2 单季化** | 累计值 → 单季值，构造 Δrcv 等辅助变量 | `02_quarterly.pkl` + 报告 | 因子建模师（`quant-factor-modeler`） | G2.1–G2.2 | 未写去累计口径、有效率 <80% |
| **S3 时点对齐** | 把每期数据挂到**公告日**，不是报告期末 | `03_asof.pkl` + 报告 | 数据工程 + 合规（`a-share-data-expert` / `capital-market-compliance-officer`） | G3.1–G3.2 | 用 period 对齐，或因子日期早于报告期 |
| **S4 因子计算** | 逐期向前回归，算残差/σ | `04_factor_raw.pkl` + 诊断 | 因子建模师（`quant-factor-modeler`） | G4.1–G4.5 | min_n<6、ddof<3、β 爆炸、样本分布未披露 |
| **S5 截面标准化** | 按 spec 的调仓间隔取网格，winsorize → 中性化 → rank | `05_factor_final.pkl` | 量纲/数据处理（`data-normalization-analyst`） | G5.1–G5.4 | 未做极值、未 rank、未中性化且无豁免 |
| **S6 评价** | IC/ICIR/NW-t/衰减/分层/多空/换手/扣费 | `06_metrics.json` | 数模分析（`quant-indicator-analyst`） | G6.1–G6.4 | 11 项有空白、未做 NW 调整、单调性靠文字 |
| **S7 报告** | 从 metrics 程序化生成 md，判据取自 spec，不含手填数字 | `07_report.md` | 数模分析（写）+ PM（核） | G7.1–G7.4 | 未扣费、成本吃掉一半收益、缺章节 |

## 三、26 条门禁（代码化，不是清单）

| ID | 阶段 | 判据 | FAIL 的后果 |
|---|---|---|---|
| G0.1 | S0 | 必填项齐备 | 口径不全，后面全白做 |
| G0.2 | S0 | 成本 > 0 | 扣费结论无意义 |
| G1.1 | S1 | ≥50 只 × ≥8 个公告日 | 统计不可靠 |
| G1.2 | S1 | 核心字段缺失率 ≤10% | 需说明丢弃机制 |
| G1.3 | S1 | 股票池过滤按 spec 执行且已披露 | spec 写了但代码没执行 = 股票池未定义 |
| G2.1 | S2 | 去累计口径已写明 | Q1 是否跨年差分不可知 |
| G2.2 | S2 | 单季值有效率 ≥80% | 数据源有缺口 |
| **G3.1** | S3 | **必须 ann_date 对齐** | **前视 2–4 个月** |
| **G3.2** | S3 | 因子日期 ≥ 报告期 | 隐性前视 |
| G4.1 | S4 | min_n ≥ 6（残差 df ≥3） | σ 只用 1 个自由度估 |
| **G4.2** | S4 | **ddof ≥ 3** | **σ 低估 → 因子放大 1.3–2.0 倍** |
| G4.3 | S4 | σ 放大系数 ≤1.15 | 分母仍偏小 |
| G4.4 | S4 | \|β\|≤1.5 且 β 跨股票 σ≤0.8 | 估计被少数期主导 |
| G4.5 | S4 | 样本量分布已披露 | 排序混入"数据完整度" |
| G5.1 | S5 | 极值处理开启 | 单只异常主导分层 |
| G5.2 | S5 | 截面标准化开启 | 不同股票尺度不可比 |
| G5.3 | S5 | 中性化或书面豁免 | 可能只在排行业/市值 |
| G5.4 | S5 | 预处理保留 ≥90% | 截面变薄 |
| **G6.1** | S6 | **11 项指标无空白** | 不可复核 |
| G6.2 | S6 | 独立截面 ≥20 | ICIR/t 不可靠 |
| G6.3 | S6 | 已做 NW-t | 重叠样本 t 值虚高 |
| G6.4 | S6 | 单调性程序判定 | 用"近乎完美"糊过去 |
| **G7.1** | S7 | **成本已扣** | 毛收益不能作证据 |
| G7.2 | S7 | 成本 < 毛利一半 | 策略不可实施 |
| G7.3 | S7 | 报告无 TODO/nan | 未完成 |
| G7.4 | S7 | 五节齐全 | 缺节不可验收 |

门禁分三态：**PASS / WARN / FAIL**。WARN 不阻断，但必须在执行记录里写"为什么接受"——这是给人留的判断位，不是给人留的后门。

## 四、三条红线（为什么是这三条）

1. **时点（G3）**：用报告期末当可得日，因子就会提前 2–4 个月"知道"财报。所有 IC 都虚高，且这种错误在代码里看不出来——它只是 `merge` 的一个参数。
2. **σ（G4.2）**：残差除以 σ 是标准做法，但 σ 的估计要扣掉三个参数。`ddof` 写 0 或 1，因子会被放大 1.3–2.0 倍，而放大倍数取决于该股票的**历史长度**——排序于是混入"上市多久"这个伪变量。T-OCFS-01 审计里这条是 P1 首条。
3. **成本（G7.1）**：21 日调仓、单边换手 40%，双边成本约 12–20bp/期，年化 2–5%。不扣费的"多空年化 5%"可能扣完就剩 1%。

## 五、接一个新因子：只改 spec，不动代码

```bash
cp config/factor_spec.example.json config/my_factor.json
# 改四处：name / formula.type / formula 参数 / evaluate 参数
python src/run.py --spec config/my_factor.json --out runs/my_factor
```

目前 `formula.type` 支持 `ocfs_residual`（经营现金流 surprise）。要接新公式，只需在 `stages.stage4_factor` 里加一个分支——**其余七阶段与全部门禁自动复用**，这是骨架的主要价值。

## 七、门禁自己也要被测试

`tests/test_gates.py` 做反例注入：故意把流水线改错，断言对应门禁必须 FAIL。

```
T1 正常路径 0 FAIL
T2 报告期末对齐 → G3.1 FAIL
T3 ddof=0 + min_n=4 → G4.1、G4.2 FAIL
T4 不中性化且无豁免 → G5.3 FAIL
T4b 有豁免 → 放行
T5 成本 0 → G0.2、G7.1 FAIL
T6 缺夏普 → G6.1 FAIL
T7 无单调性判定 → G6.4 FAIL
T8 成本占毛利过高 → G7.2 WARN
```

**这一步不能省**：没有反例测试的门禁，很可能是一条永远 PASS 的空规则——那比没有门禁更危险，因为它会给人"已经检查过"的错觉。

## 八、PM 的角色边界

| PM 做 | PM 不做 |
|---|---|
| 写任务单（阶段、责任方、判据、截止） | 写因子代码 |
| 跑 `run.py` 看门禁结果 | 调参让门禁通过 |
| 判 WARN 是否可接受并留痕 | 把 FAIL 改成 WARN |
| 打回时只写"缺什么、在哪、补成什么样" | 替执行方设计解法 |
| 记录异议与变更 | 自己验收自己 |

PM 的验收工具就是 `08_gates.json`——它比人可靠的地方是**不会因为赶进度就放过 G3.1**。

## 九、谁来做：代码、专家、还是人

骨架里**没有任何一步是「交给 agent 自己看着办」**。三类主体分工明确：

| 类型 | 承担者 | 具体内容 | 可否替代 |
|---|---|---|---|
| **算** | 代码 | 单季化、公告日对齐、回归、标准化、IC、分层、净值、换手 | 不可，也不需要 agent |
| **卡** | 代码 | 26 条门禁，PASS/WARN/FAIL | **禁止 agent 改判** |
| **定口径** | 专家 | 公式定义、去累计方式、回归设定、中性化方案 | 需要专家判断 |
| **解释** | 专家 | 有无经济逻辑、是否只是行情 beta | `market-regime-analyst` 协作 |
| **放行** | PM | 判 WARN、判"算得对不对"、出验收结论 | **只能 PM** |

**为什么不让 agent 参与门禁判定**：执行者一旦能影响判定，就有动机让自己的结果通过。所以门禁必须是与执行方无关的确定性代码。

绑定表在 `config/owners.json`，一条命令可查：

```bash
python src/run.py --owners
```

| 阶段 | 负责角色 | 绑定专家 | 代码入口 |
|---|---|---|---|
| S0 规格 | 因子建模师 | `quant-factor-modeler` | `stage0_spec` |
| S1 数据与股票池 | 数据工程 | `a-share-data-expert` | `stage1_ingest` |
| S2 单季化 | 因子建模师 | `quant-factor-modeler` | `stage2_quarterize` |
| S3 时点 | 数据工程 + 合规 | `a-share-data-expert` / `capital-market-compliance-officer` | `stage3_asof` |
| S4 计算 | 因子建模师 | `quant-factor-modeler` | `stage4_factor` |
| S5 标准化 | 量纲处理 | `data-normalization-analyst` | `stage5_standardize` |
| S6 评价 | 数模分析 | `quant-indicator-analyst` | `stage6_evaluate` |
| S7 报告 | 写 + 核 | `quant-indicator-analyst` / `project-delivery-manager` | `stage7_report` |

门禁结果 `08_gates.json` 里每条都带 `owner` / `expert` / `human_review`，PM 拿到 FAIL 时能直接知道找谁、该看什么。

**不外包给 agent 的三件事**：门禁判定、spec 变更（必须走变更单）、验收结论。
